每個預熱後的數字代表重新啟動 SoundCraft 並重新開啟同一份專案後的第一次有聲回呼。原安裝版數字取自前輪同一路徑的硬體紀錄。計時包含 Windows 排程，不能當作所有演出環境的最壞時間。

64 取樣最接近上限的一次，整個回呼為 1.4482 ms，距離 1.45125 ms 的期限僅約 0.003 ms。這兩次冷啟動通過；長時間負載的餘裕仍待另測。硬體驗收後，原廠面板已恢復 256 取樣。修正版保存在本機獨立測試目錄。

## 為何第一個區塊特別慢

以與安裝版相同的 317b8fe 原始碼編譯 Windows x64 VST3。在 128 取樣的分段診斷中，48 kHz 專案的一次外掛呼叫處理 140 個專案取樣，共 10.639 ms。合成填充占 10.613 ms，其中音訊執行緒編譯 SH‑2 韌體指令占 7.756 ms，重建效果器 MEG 程式占 0.198 ms。初始 XG 參數讀取為 0.004 ms，延後還原專案狀態為 0。本機的啟動快取還原了模擬器狀態，但沒有這些已編譯指令。分段數字互有包含，不能相加。另一次同編譯器重建的舊版量到首次 process 10.943 ms。

## 修改與回歸

在 S-MU2000 的 VST3 啟用與專案狀態還原時，由控制執行緒準備音源。用共享唯讀 ROM 的暫時音源副本探索閒置和收、放音符時經過的韌體程式區塊，在正式音源上提前編譯那些位址。效果器程式穩定且因還原而需要重建時也先準備好；遇到韌體正改寫效果器仍沿用既有的等待規則。正式音源預熱期間前進零個取樣，也收不到副本的試音。另移除 setProcessing 在音訊執行緒同步開關記錄檔的動作。

先將 ASIO 預算檢查套回舊版，128、64 都失敗。只預熱開機閒置狀態的試作在 128 仍花 7.336 ms。改用專案狀態並涵蓋音符處理後降到 2.827 ms。再將效果器提前準備後，兩次試作為 1.669、1.655 ms。表格列的是最後保留的版本。 另用原廠 vst3probe 載入專案保存的貝斯音色，播放兩個音並放鍵。前後兩份 48 kHz 立體聲 PCM 的 55,199 個取樣框逐位相同。

## Model 12 驗收

專案 Back to the Chorus 的 SHA‑256 為 992c9ea2e252052261f326a03be545683f3bf9a59d1db5ab166a0acc1d5a7071。Model 12 使用 44.1 kHz，直接由原廠 ASIO 9/10 輸出，從 MAIN USB 11/12 回錄。實體 MIDI 經 Model 12 的 DIN OUT 接回 UM‑ONE。每次起播均比對 SPP、Continue、144 個 Clock、Stop，以及實收音訊回呼的尺寸。驗收以 MAIN 錄音與銅鈸樣本的相關值大於 0.90 計數，並獨立檢查後續伴奏。

8.000 秒的 16 次均只辨認到一個銅鈸。8.125 秒的 8 次均未補播。後續音符最低相關值 0.9920。兩路擷取序號都連續。原有波形檢查共標記 0 段錄音有超過 32 個 PCM 單位的相鄰殘差變化，偵測到 0 個低電平視窗。聽感留待本人盲聽。

### 預熱後的 64／128 取樣十分鐘長播

64 取樣的五次冷啟動均有至少 0.161 ms 餘裕，但持續播放時 413,434 個回呼中有 8 個各別超時，最慢 2.943 ms。MAIN 回錄另確認一次至少 1.45 ms 的音量驟降，與最近的回呼超時相距 22.05 秒。128 取樣的 206,718 個回呼均在預算內，最慢仍餘 0.512 ms，回錄沒有達到相同門檻的掉音。兩組各自從 8.000 秒起播 5 次，銅鈸每次只響一次；從 8.125 秒起播各 5 次，均未補播。面板已恢復 256 取樣，聽感待本人盲聽。[十分鐘實測、計時圖與 MAIN 波形](soak/REPORT.zh-TW.md)

### 第 486.242 秒掉音追查

逐樣本比對確認，64 取樣第 486.242 秒的 MAIN 回錄插入 **107 個近靜音取樣（2.426 ms）**；先前的 1.45 ms 是偵測視窗長度。原始兩次區塊處理開始相隔 6.518 ms，其中 6.099 ms 落在兩段工作之間。以獨立 ASIO 客戶端重送同一段 PCM，正常交付時兩組均為 0/4，刻意延後交付時 64／128 取樣分別有 3/4、2/4 出現同型缺口。原專案另做 12 次實體 MIDI 起播，8.000 秒共 8 次各響一次，8.125 秒共 4 次均無補播。盲聽待本人回家。[實機重播與逐樣本驗收](soak/dip486/REPORT.zh-TW.md)
