# Model 12 回呼空檔的 Windows 與 USB 實測

前次在第 486.242 秒錄到 MAIN 多出 107 個近靜音取樣。兩次 SoundCraft 回呼的工作區段相隔 6.099 ms。當時的錄音與計時檔能重建音訊接點，但沒有留下 Windows 排程或 USB 事件。本次用同一份 S‑MU2000 伴奏，調查新錄到的事件能定位到哪一段。[原始逐樣本驗收](../dip486/REPORT.zh-TW.md)

## 結論與 9 分鐘實測

**原先的 6.099 ms 空檔和 107 個近靜音取樣，本輪都沒有重現。** 新資料可以分解實際發生的回呼間隔，尚無證據將原先那次掉音歸因於 SoundCraft、外掛或特定驅動。這次只調整驗收工具讀取 ASIO 檔頭的時機，SoundCraft、S‑MU2000 和伴奏沿用相同版本。盲聽待本人回家。

兩輪均從 8.000 秒 Continue，各播放 9 分鐘，實體 MIDI 迴路每輪收到 25,920 個 Clock 和 Stop。各自在 ASIO 9/10 與 MAIN 回錄找到 34 次預期的銅鈸起音，包含起播時的第一下。8.125 秒不補播沿用[上一輪四次實測](../dip486/REPORT.zh-TW.md)，本輪的重點是持續播放期間的回呼。

### Chrome 遠端桌面與實體 MAIN 同步回錄

將 Windows Application 事件來源 `chromoting`（1 連線、2 中斷）與第一個 MIDI Clock、ASIO 區塊的主機時間對齊。2026-11-21 臺北時間 08:48:57.935 至 08:49:56.446 有遠端工作階段。64 取樣九分鐘播放自 08:49:06.690 開始，前 49.756 秒與工作階段重疊。第 13.498 秒的 MAIN 插入就在這段期間。8 次回呼超時中，前 5 次發生在連線中，其餘 3 次在斷線後。128 取樣自 08:58:39.809 起的九分鐘全程無連線。這兩次實測同時存在緩衝大小、連線狀態與起播經過時間等差異，無法從次數判定因果。事件摘錄只保留連線狀態和時間。[連線紀錄](splice-usb/remote-session-times.json)

Chromium 在 Windows 上讀取預設播放端點以供遠端傳輸。這份 SoundCraft 專案直接開啟 Model Mixer ASIO 並送到 9/10。兩者可以並行。遠端擷取、編碼及傳輸是可能的系統負載，這份連線紀錄無法量出它在該次回呼佔用的時間。[Chromium Windows 音訊擷取](https://chromium.googlesource.com/chromium/src/+/HEAD/remoting/host/audio_capturer_win.cc) · [當輪實際 ASIO 設定](../usb64r/route.json)

**實體雙路重測尚待接線。** 已核對原伴奏專案與 SoundCraft 執行檔 SHA-256 均與上輪一致。規劃以相同 44.1 kHz 伴奏各播九分鐘，64／128 兩輪皆維持相同的遠端連線狀態，優先全程斷線。兩輪各自核對 ASIO 檔頭的實際緩衝大小。Model 12 支援同時使用 SD 多軌錄音與 USB 音訊，SD 的兩條實體回接軌可作為獨立於電腦 USB 回錄的紀錄。[原廠方塊圖](https://www.tascam.eu/en/docs/Model12_SettingsPanel-V2_block-diagram.pdf) · [Model 12 錄音說明](https://www.tascam.eu/en/docs/Model12_OM_EFS_RevF.pdf)

### 排程與回呼的對時

以 UTC 時間對齊；回呼開始以結束時間減去該次計時所得。從測試程序的執行緒中，以回呼中點落在實際上 CPU 的次數辨識，再用啟動位址交叉核對。兩輪最高者均由 TASCAM 的 `us_asio.dll` 啟動，分別命中 83,886／83,891、41,948／41,949 個中點，含起播前與停止後。兩組 ETW 核心及事件收集器均回報 0 個遺失事件。[64 排程](partition-64.json) · [128 排程](partition-128.json) · [64 收集狀態](status-64.log) · [128 收集狀態](status-128.log)
